# OpenHR20

[![Reliability build](https://github.com/joker-mik/OpenHR20/actions/workflows/reliability-build.yml/badge.svg)](https://github.com/joker-mik/OpenHR20/actions/workflows/reliability-build.yml)

OpenHR20 is open firmware for Honeywell Rondostat HR20 and related ATmega-based radiator thermostats. It is a complete open-source firmware implementation rather than a modification of Honeywell's proprietary firmware. The project was started around 2008 by Jiri Dobry and Dario Carluccio and has since been extended by many contributors.

This fork keeps the original HR20/HR25 functionality while focusing on reliable builds, safer motor and calendar handling, runtime window-detection selection, and optional RFM12B support.

Supported thermostat families:

- Honeywell HR20
- Honeywell HR25
- Thermotronic

The historical project is still available on [SourceForge](https://sourceforge.net/projects/openhr20/). A detailed German description of the original project is available at [mikrocontroller.net](https://www.mikrocontroller.net/articles/Heizungssteuerung_mit_Honeywell_HR20).

## Quick start

Flashing OpenHR20 requires an AVR programmer and basic AVR experience. The thermostat MCU is normally programmed through its external connector/JTAG interface.

The safest default build is the plain HR20 without radio:

```sh
make
```

For the current HR20 universal JD_INTERNAL firmware:

```sh
make HR20_universal_jd
```

The universal build contains local thermostat operation, optional RFM12B radio with runtime module detection, RFM frequency tuning, and runtime selection between software and PE2 hardware window detection. It uses the JD_INTERNAL RFM wiring so PE2 remains available for a window contact and the JTAG pins are not consumed by the radio.

See [Build targets](#build-targets) for the other hardware/wiring variants.

## User interface

The HR20 is fully usable locally; an RFM gateway or UART connection is not required for normal thermostat operation.

The front panel provides the **PROG**, **C**, and **AUTO** keys plus the rotary wheel.

### Normal operation

| Control | Action |
| --- | --- |
| Wheel | Change the requested temperature |
| AUTO | Change operating mode |
| C | Cycle the alternate home displays: room temperature, valve position, time, and battery display when enabled |
| Long AUTO | Enter date/time setting |
| Long PROG | Enter switching-time/program setting |
| Long C | Enter preset-temperature setting |
| Long key combination detected as `ALL` | Enter service menu |
| Long lock combination | Toggle key lock |

While editing values, the wheel changes the selected value and **PROG** normally confirms it. **AUTO** is used to leave several setting/service screens without saving the current edit.

The exact long-press combinations are generated by the keyboard state machine and can differ between supported thermostat hardware. See `src/keyboard.c`, `src/keyboard.h`, and `src/menu.c` when servicing or adapting another model.

### Service menu

The service menu exposes configuration bytes directly:

- wheel: select configuration index or change its value;
- PROG: enter value editing / save the edited value;
- AUTO: leave the service menu;
- C: switch to the watch/debug view.

Configuration values, defaults and valid ranges are defined in `src/eeprom.h`. Incorrect service values can affect motor control, temperature regulation, radio settings and other low-level behaviour, so changes should be made deliberately.

## Window detection

The current standalone HR20 firmware and `HR20_universal_jd` can contain both window-detection implementations and select the mode at runtime.

The runtime configuration value `window_detection_mode` supports:

| Value | Mode |
| ---: | --- |
| 0 | window detection off |
| 1 | software detection from temperature change |
| 2 | hardware window contact on PE2 |

The default is software detection.

The hardware mode also has configurable opening and closing delays. Software mode has configurable temperature-change thresholds, sample times and maximum open time. These values are part of the EEPROM configuration and can be edited through the service/configuration interface.

**Important:** PE2 cannot simultaneously be the hardware window-contact input and the RFM SDO pin. This is why the MARIOJTAG radio wiring is incompatible with hardware window detection, while JD_INTERNAL leaves PE2 free.

## RFM12B radio

RFM support is optional. The recommended HR20 radio wiring for the universal build is **JD_INTERNAL**:

| RFM signal | ATmega169 pin |
| --- | --- |
| SCK | PF1 |
| SDI | PF0 |
| nSEL | PA3 |
| SDO | PE6 / PCINT6 |
| nIRQ | not connected |

`HR20_universal_jd` performs runtime RFM detection. The same firmware can therefore run with the JD_INTERNAL radio fitted or without the module. When detected, normal RFM initialization, encrypted communication and frequency tuning are enabled.

Other supported radio wirings are retained for compatibility:

- **MARIOJTAG**: PF4/TCK, PF6/TDO, PF5/TMS and PE2/PCINT2. It consumes JTAG pins, requires JTAG to be disabled, and conflicts with a PE2 hardware window contact.
- **TK_INTERNAL**: HR25-specific internal wiring.

The RFM protocol is the project's existing proprietary sub-GHz protocol; it is not Bluetooth/BLE.

## UART interface and commands

Non-RFM HR20 builds enable the local UART at **9600 baud**. RFM builds intentionally do not compile the local UART command parser; their corresponding commands are transported through the wireless protocol instead.

The external connector exposes RXD on PE0 and TXD on PE1. Commands are line-oriented and terminated by a newline. Command letters are uppercase; hexadecimal arguments use lowercase hexadecimal digits.

### Local UART commands

| Command | Meaning |
| --- | --- |
| `V\n` | Print firmware version |
| `D\n` | Print status/debug line |
| `Taa\n` | Read watch/debug variable `aa` |
| `Gaa\n` | Read configuration byte `aa`; address `ff` returns EEPROM layout version |
| `Saadd\n` | Write configuration byte `aa` with value `dd` |
| `Rab\n` | Read timer for day `a`, slot `b` |
| `Wabcddd\n` | Write timer: day `a`, slot `b`, mode `c`, time `ddd` |
| `Yyymmdd\n` | Set date; values are hexadecimal |
| `Hhhmmss\n` | Set time; values are hexadecimal |
| `Axx\n` | Set requested temperature, in 0.5 °C units |
| `Mxx\n` | Set mode / close window; `00` manual, `01` auto, `fd` leaves mode unchanged and closes window state |
| `Lxx\n` | Key lock: `00` unlock, `01` lock, `02` query |
| `B1324\n` | Reboot |

Most local commands are controlled by the firmware's `ENABLE_LOCAL_COMMANDS` build option. The parser implementation in `src/com.c` is the authoritative protocol reference.

### Wireless commands

The RFM command parser supports the corresponding binary command operations including version/status, watch/config access, timers, reboot, mode, requested temperature and key lock. Unlike the UART representation, wireless command arguments are binary bytes rather than ASCII hexadecimal text.

## Build targets

The top-level Makefile provides explicit targets so wiring and hardware choices are visible rather than hidden behind implicit defaults.

| Target | Hardware / purpose |
| --- | --- |
| `HR20_universal_jd` | HR20 universal build; optional JD_INTERNAL RFM, local operation, runtime SW/PE2 window detection |
| `HR20_original_sww` | HR20 without RFM; runtime SW/PE2 window detection |
| `HR20_original_hww` | Compatibility name for the standalone HR20 runtime-window build |
| `HR20_rfm_int_sww` | HR20 with JD_INTERNAL RFM and software window detection |
| `HR20_rfm_int_hww` | HR20 with JD_INTERNAL RFM and hardware window detection |
| `HR20_rfm_ext_sww` | HR20 with MARIOJTAG RFM, software window detection, JTAG disabled |
| `HR25_original_sww` | HR25 without RFM |
| `HR25_rfm_int_sww` | HR25 with TK_INTERNAL RFM |
| `thermotronic_sww` | Thermotronic without RFM |
| `rfm_master` | Separate RFM master/gateway firmware |

To build all supported targets:

```sh
make all
```

The CI builds the thermostat/radio matrix, performs static checks and EEPROM-layout checks, and enforces the ATmega169P flash/RAM limits for the universal HR20 build.

## Compiling

An AVR-compatible GCC cross-compiler and AVR libc are required. On Debian-based Linux systems these are commonly provided by `gcc-avr` and `avr-libc`; `avrdude` can be used for flashing.

The reliability CI uses a pinned AVR-GCC toolchain so firmware-size checks are reproducible.

Build artifacts are written below `bin/<target>/` and include the firmware HEX, EEPROM image, ELF/map files and a text file containing build metadata and memory usage.

Examples:

```sh
make HR20_original_sww
make HR20_universal_jd
make HR20_rfm_ext_sww
make HR25_original_sww
```

## HR20 external connector pinout

The external HR20/HR25 connector can be used for programming/JTAG and wired UART communication.

| ATmega169PV | Function / MCU pin |  |  |  |
| --- | --- | --- | --- | --- |
| Vcc | RXD (PE0/02) | TDO (PF6/55) | TMS (PF5/56) | /RST (PG5/20) |
| GND | TDI (PF7/54) | TXD (PE1/03) | TCK (PF4/57) | PE2/04 |

For the universal JD_INTERNAL radio build, the JTAG pins remain available because the RFM module uses PF1/PF0/PA3/PE6 instead.

## Reliability notes

This fork contains additional checks and defensive handling around motor calibration, RTC/date handling, communication parsing, EEPROM layout, RFM runtime detection and firmware memory limits.

The universal HR20 build is intentionally kept below the ATmega169P's 16 KiB flash and 1 KiB SRAM limits. CI fails if those limits are exceeded.

Hardware testing remains important, especially for motor calibration, PE2 window-contact polarity/wiring and optional RFM module detection.
